### 0.3 范围与对外承诺

本轮"跨框架桥接"具体指：**Vue 3 宿主嵌入 React 18/19 子应用、React 18/19 宿主嵌入 Vue 3 子应用**，以插件定义的桥接契约整站挂载/卸载，props 快照、会话代次、加载失败恢复、dev 与生产部署均有真实验证。

**明确不做（与 §12 边界声明一致，文档必须写在一起）：**

- 组件级混渲染：Vue 模板里直接渲染 React 组件（veaury 式互转）不做，那是框架桥接库的产品；
- 子应用路由与宿主 URL 同步：v1 子应用用 memory 路由，URL 同步列为后续方向，不在本轮承诺；
- Angular 及其他框架：无适配层、无验证、不承诺；用户可按公开契约自行实现桥接导出，但插件不背书；
- SSR / RSC / Node 端加载、沙箱、CSS 隔离：继续在支持面外。

桥接只隔离两棵组件树的挂卸边界，不提供浏览器 realm 隔离。远程全局 CSS、`body`/`html` 样式、全局变量与通过 React Portal / Vue Teleport 放到容器外的 DOM 仍可影响宿主；`unmount` 不能承诺撤销浏览器已加载的共享 CSS。README 必须给出样式命名空间与全局副作用自行清理的接入要求，不能把“容器 DOM 清空”写成“子应用全部副作用已隔离”。

## 1. 背景与决策记录

当前 5.2.2 的支持面是 Vue 3 与 React 18/19 各自的浏览器端联邦，跨框架可消费纯 TS 模块；尚无子应用级桥接 API。README §12 声明不支持 Vue/React 组件直接混渲染。Module Federation Bridge 提供子应用级生命周期封装，可供产品范围参考，但其实际 API 不是本文的 `mount/unmount` 签名。

已拍板决策（不得在实施中推翻）：

1. 采用下一个未占用 minor；以 5.2.2 为本次文档基线时，候选为 5.3.0。版本选择以实施当天 Git tag 与 npm registry 为准。
2. 同包新增 `/bridge` 导入点，不建独立 npm 包（理由：vue/react 已是 optional peer、桥接层重度复用运行时内部、单人维护双包是纯负担）。
3. v1 范围 = 双向子应用级嵌入 + 会话代次打通 + dev/prod 双引擎验证；路由同步不做。
4. 组件级混渲染继续不做，§12 边界声明保留并精确化。

本文定型决策已由作者拍板确认（2026-09-29，与上方四项同级生效，实施中不得推翻）：

- **D1 契约式而非组件式**：子应用导出本插件自定的 `mount/unmount` 契约对象，不是裸根组件。Vue 子应用可在自己的 `createApp` 中装配 router、pinia 等插件；宿主侧按宿主框架提供两个工厂即可覆盖双向组合。该思路借鉴子应用生命周期生态，不宣称与其他产品的函数签名兼容。
- **D2 API 命名**：宿主侧工厂叫 `createVueBridgeApp`/`createReactBridgeApp`；子应用侧 `defineBridgeApp` 在 `/runtime` 与 `/react` 同名双导出。`/bridge` 是优先入口；若它在 dev 强制提前执行对向适配器，按 §3.1 增加按宿主框架分离的入口，名称不变。
- **D3 新错误码**：MFU-015（桥接契约非法）、MFU-016（桥接准备或生命周期失败，`details.phase` 区分 getContext/mount/unmount）、MFU-017（桥接会话参数与 AppContext 不一致）。现用码为 MFU-001~014；实施前再次核对占用情况。
- **D4 体积预算**：桥接宿主入口 gzip 目标 ≤ 4096B（框架外置、zlib level 9）；若按 §3.1 拆分，分别测两个推荐入口及聚合入口，避免只测空壳。`dist/runtime.js` ≤ 9216B、`dist/react-adapter.js` ≤ 4096B 是 5.2.2 的现行门禁。新增逻辑先测前后值；确需上调门禁时解释增量并同步脚本、CHANGELOG，不能沿用旧任务书的 3072B 数字或悄悄放行。

## 3. 契约与目标 API（唯一约定）

### 3.1 导入入口

```text
构建期        @fulgurjs/federation -> dist/index.js（不变）
Vue 子应用    /runtime  -> 现有导出 + defineBridgeApp
React 子应用  /react    -> 现有导出 + defineBridgeApp
桥接宿主      /bridge   -> createVueBridgeApp + createReactBridgeApp + 契约类型（新增）
```

- `/bridge` 为浏览器 ESM 入口，与 `/runtime`、`/react` 同样不承诺 `require()`，不新增 CJS 浏览器入口。
- 优先保持一个 `/bridge` 公共入口，但必须同时测 dev 原生 ESM 请求图与生产产物：只使用 `createVueBridgeApp` 的宿主页不能在首次挂载前执行 React 宿主适配器、`react-dom/client` 或 React 远程业务代码；反向同理。ESM 静态 re-export 在 dev 无摇树保证；若单入口做不到按宿主框架懒加载，**必须**增加 `/bridge/vue`、`/bridge/react` 两个按宿主框架分离的入口作为推荐用法，根 `/bridge` 可保留兼容聚合但应说明加载代价。不得为了维持单入口而牺牲 BR01 的按需加载目标。
- 纯 Vue / 纯 React 项目的依赖隔离不受影响：`/runtime` 新增导出不引 React，`/react` 新增导出不引 Vue；导入图测试同步加断言。
- **桥接用户必须同时安装两套框架**（宿主 package.json 含 vue + react + react-dom），shared 双框架 singleton 为强制配置。这是桥接模式的使用合同，README 必须显著写明，且不破坏"纯项目零对方依赖"承诺。

### 3.2 桥接契约 `BridgeApp`

所有相关入口共享同一类型定义（对消费者从子应用入口或最终确定的宿主入口导入均可）：

```ts
export interface BridgeApp {
  /** 首次根提交完成时才算挂载成功；同一容器未卸载前重复 mount 是契约违例 */
  mount(el: HTMLElement, props?: Record<string, unknown>): void | Promise<void>
  /** 同步使当前挂载代次失效并清理已创建的 root；未知容器为 no-op */
  unmount(el: HTMLElement): void
}
```

- 契约实现内部状态必须**按容器 el 分键**：同一契约模块被页面多处挂载时各实例互不干扰，这是可测行为不是文档愿景。
- `mount` 返回 `void` 表示首次根提交已同步完成；返回 Promise 时，宿主保持 pending，直到该 Promise 在首次根提交后完成。这里的“完成”不等待子应用所有异步数据、路由页面和懒加载组件。首次根提交前的失败必须让 `mount` 抛错或拒绝，并由宿主转成 MFU-016（`phase: 'mount'`）；首次提交后的子应用内部错误由子应用自己的错误边界负责（§4.4）。
- `unmount(el)` 在挂载仍 pending 时也必须立即使该容器的本轮代次失效，并清理已经创建的 app/root。之后迟到的 Promise 成功或失败不能重建 DOM、改写宿主状态或造成未处理拒绝；实现方对已创建资源负责清理。宿主不依赖异步 `unmount` 等待清理。重复 mount 必须拒绝且不覆盖原实例。
- `mount` 抛错或拒绝时，`defineBridgeApp` 必须清理已创建的 app/root，不留半挂状态；宿主占位转错误态。`unmount` 抛错时宿主捕获并按 MFU-016（`phase: 'unmount'`）报告，不能使宿主框架崩溃；该容器清理状态不确定，不得直接在同一 `el` 上启动新 root 或宣称无泄漏。实现方尽力完成剩余清理，宿主显示可操作的失败状态；实际残留在报告中如实记录。自定义契约也必须遵守以上时序，不能只返回一个延迟任务而忽略卸载。
- 远程 expose `./bridge` 的模块**默认导出**契约对象；插件校验 `mount/unmount` 均为函数，否则 MFU-015。

### 3.3 子应用侧 `defineBridgeApp`

```ts
// Vue 子应用 src/bridge.ts —— /runtime 导出
import { createApp } from 'vue'
import { createMemoryHistory, createRouter } from 'vue-router'
import { defineBridgeApp } from '@fulgurjs/federation/runtime'
import App from './App.vue'
import { routes } from './routes'

export default defineBridgeApp((props) => {
  const app = createApp(App, props)
  app.use(createRouter({ routes, history: createMemoryHistory() }))
  return app
})
```

```tsx
// React 子应用 src/bridge.tsx —— /react 导出
import { MemoryRouter } from 'react-router-dom'
import { defineBridgeApp } from '@fulgurjs/federation/react'
import App from './App'

export default defineBridgeApp((props) => (
  <MemoryRouter>
    <App {...props} />
  </MemoryRouter>
))
```

- Vue 形态：工厂接收 props 快照、返回已装配完整的 `VueApp`；helper 负责 `app.mount(el)` / `app.unmount()` 与按 el 的实例跟踪。helper 可用已有 Vue 依赖，不引 React；`/runtime` 导入图仍须零 React。
- React 形态：工厂返回 ReactElement；helper 负责 `createRoot(el).render(...)` / `root.unmount()`。`root.render()` 返回不表示首屏已提交；helper 需用根内提交探针与首次渲染错误边界兑现 §3.2 的 Promise 语义，首屏渲染错误不能被误报为挂载成功。`react-dom/client` 应在实际 mount 时按需取得，避免只使用现有 `/react` API 的消费者提前加载桥接挂载逻辑；外置与共享子路径机制须兼容，React 18/19 分别实测。
- 远程的 `fulgurjs.config.ts` 在 exposes 增加 `'./bridge': './src/bridge.ts'`（React 例对应 `.tsx`）；setup/onSession 沿用现有语义，无桥接专用初始化。示例需把 `vue-router` 或 `react-router-dom` 列为远程工程的直接依赖。

### 3.4 宿主侧工厂（`/bridge`）

```ts
// Vue 宿主：业务数据只放 appProps；sessionKey 是宿主控制参数
import { createVueBridgeApp } from '@fulgurjs/federation/bridge'
import { getLatestHostContext } from './host-context'
const RemoteReactApp = createVueBridgeApp('remote-react/bridge', {
  retries: 1,
  getContext: () => getLatestHostContext(),
})
// <RemoteReactApp :session-key="loginKey" :app-props="{ userId: uid, onReady: handleReady }" />
```

```tsx
// React 宿主
import { createReactBridgeApp } from '@fulgurjs/federation/bridge'
import { getLatestHostContext } from './host-context'
const RemoteVueApp = createReactBridgeApp('remote-vue/bridge', {
  fallback: <p>加载中…</p>,
  getContext: () => getLatestHostContext(),
})
// <RemoteVueApp sessionKey={loginKey} appProps={{ userId: uid, onReady: handleReady }} />
```

`getLatestHostContext` 是宿主自行提供的纯同步业务函数，返回当前 user、sessionKey 等完整 AppContext；示例工程必须提供可运行实现。`getContext` 只返回快照，不调用 `provideAppContext`、不修改全局状态，也不启动异步回填。桥接层先校验返回值和受控 `sessionKey`，再自行调用 `provideAppContext`，然后才调用 `loadRemote`。现有 `provideAppContext` 是顶层 merge，**换账号时宿主须先让旧桥接组件收到 `sessionKey: null` 并卸载，再调用一次 `clearAppContext()` 清除 A 的字段，准备 B 的完整 context，最后设置 B 的新 `sessionKey`**；不能只用 `provideAppContext(B)` 覆盖同名字段。`getContext` 用于首次、重试及换会话时获取最新快照，不承担全局登出清理。若 §3.1 因导入图验证改用分入口，上述两个宿主导入路径同步改为 `/bridge/vue` 和 `/bridge/react`。

| 项 | Vue 宿主（`createVueBridgeApp`） | React 宿主（`createReactBridgeApp`） |
|---|---|---|
| 工厂选项 | `loadingComponent?`、`errorComponent?`、`retries?`、`timeout?`；`getContext?: () => Partial<AppContext> & Record<string, unknown>` 在首次、重试及换会话的实际加载前**同步返回**本次所需的上下文快照 | `fallback?`、`error?`（节点或 `(error, retry) => ReactNode`）、`retries?`、`timeout?`；同一 `getContext?` 语义 |
| 返回组件的 props | `appProps: P` 是子应用业务数据；`sessionKey?: string \| null` 是桥接控制参数，不能混入 `P` | 同左；返回 `React.ComponentType<{ appProps: P; sessionKey?: string \| null }>` |
| 泛型 | `createVueBridgeApp<P>(spec, options?)`，P 只约束 `appProps` 的形状 | 同左 |
| spec | 直接传完整 `<remote>/<expose>`，与 `remoteComponent(spec)` 同一解析规则；单组件工厂没有 `remotePrefixes/schema/deriveSpec` 选项 | 同左 |
| 占位默认 | 内置中文诊断及「重试加载 / 刷新页面重试」操作（§4.4） | 同左 |

不新增同义选项（Vue 不收 `fallback`，React 不收 `loadingComponent`）；不为简单场景强制建配置；非法参数（负数 retries、NaN timeout 等）按现行诊断风格处理。

两个宿主包装组件只把 `appProps` 的浅拷贝传给 `contract.mount`；`sessionKey`、宿主组件的 `key/ref`、容器 `class/style` 与框架事件不混入业务 props。`appProps.onReady` 是显式回调函数，不经 Vue `emit` 自动跨 root。容器外观可由宿主外层元素控制；v1 不提供第二套样式透传 API。类型检查和双向浏览器测试须覆盖回调、保留对象引用及控制参数不泄漏。

### 3.5 shared 强制配方（桥接模式）

```ts
// 桥接宿主 fulgurjs.config.ts：宿主安装 vue、react、react-dom
shared: {
  vue: { singleton: true },
  react: { singleton: true },
  'react-dom': { singleton: true },
}
```

Vue 子应用只需安装并共享 `vue`；React 子应用只需安装并共享 `react`、`react-dom`。如同一应用既作宿主又 expose 两类子应用，按实际角色安装并配置两套框架。不得要求纯 Vue 远程为桥接安装 React，或纯 React 远程安装 Vue。共享子路径（`react/jsx-runtime`、`react/jsx-dev-runtime`、`react-dom/client`）必须沿用并实测 5.2.2 已有处理；不能仅看上述三个键就断言单实例。README 写清双方依赖与 shared 配方，缺 singleton 的真实故障按 BN05 记录。

## 4. 精确语义

### 4.1 生命周期链

```text
宿主渲染桥接组件（sessionKey !== null） -> getContext? -> 校验返回快照或已有 AppContext 与受控 sessionKey
  -> 若有快照，由桥接层 provideAppContext
  -> loadRemote('remote/bridge') -> 容器协商 + 可选 setup/onSession
  -> 契约校验（MFU-015） -> contract.mount(el, appPropsSnapshot)（失败 MFU-016）
  -> 子应用整站运行（内部自管路由/状态）
宿主卸载 / sessionKey 变化或变 null / key 重建 -> 作废旧请求 -> contract.unmount(el)
```

### 4.2 props：快照 + 函数引用，非响应式

`appProps` 在挂载时**浅拷贝顶层字段**传入，保留嵌套对象、响应式 store 与函数的原引用；不做深拷贝或冻结。之后的 `appProps` 顶层替换**不追踪、不重渲染子应用**，需要重置时由宿主用 `:key` / key 重建组件实例。函数也是挂载时传入的引用：若宿主重渲染生成了一个新闭包，子应用不会自动拿到新函数；实时读取宿主状态应传稳定回调，让它读取当前 ref/store，或主动重挂。跨 root 不继承宿主 Vue provide/inject、Pinia 安装、React Context 或路由；需要的数据与能力必须通过 `appProps`、现有 AppContext、共享实例或子应用自己的安装步骤显式提供。

### 4.3 重挂条件与会话代次

| 触发 | 行为 |
|---|---|
| 首次渲染，`sessionKey` 为非空字符串 | 调 `getContext`（若提供），先校验返回快照的 sessionKey；无 getter 时校验现有 AppContext；桥接层提供合格快照后再 loadRemote + mount；远程 onSession 使用同一代次 |
| 首次渲染，`sessionKey` 省略（`undefined`） | 不启用桥接的受控会话校验；仍可按需调用 `getContext` 并提供快照，或复用已有 AppContext。远程若声明 onSession，沿用 runtime 对实际 AppContext.sessionKey 的判断：有值则执行，无值则 MFU-013。公开子应用不依赖此字段 |
| `sessionKey` 从字符串变为新的非空字符串 | 推荐宿主先将受控 prop 置 `null` 并等待旧桥接组件卸载，再 `clearAppContext()`，准备 B 的完整快照并更新受控 prop；桥接新代次执行 getContext + loadRemote + mount。若宿主直接 A→B，包装组件必须先作废并卸载 A，确认完成后才能给 B 写 context 与挂载；旧账号内容不得在 B 加载期间留在容器 |
| 登出：`sessionKey` 从字符串变 `null` | 立即作废旧加载并卸载；保持空容器，不再 loadRemote；等下一次非空代次。宿主在桥接组件卸载后调用 `clearAppContext()` 清除全局会话状态，并移除或禁用缓存的私有页面 |
| 同会话宿主重渲染或只换 `appProps` 引用 | 不重挂、不重复 loadRemote；顶层业务数据仍是上次挂载快照 |
| 用户点击错误占位「重试加载」 | 重建加载尝试；已成功模块经运行时缓存复用；失败入口/expose 可按现有恢复机制换 URL 重取 |

`sessionKey` 是桥接组件的显式受控输入，使用非敏感且每次登录/重登唯一的代次 ID。宿主更换账号时必须更新该 prop；桥接不订阅全局 AppContext，也不从业务 props 猜登录状态。`getContext` 必须是无副作用的同步 getter，返回对象快照，不得写 AppContext 或返回 Promise；需要异步获取用户资料时，宿主先完成准备，再让桥接组件进入可挂载状态。桥接层对 getter 的返回值先检查对象形态并拒绝 thenable，再检查其 `sessionKey` 与受控字符串相同，**通过之后**才调用 `provideAppContext`；否则旧账号快照不得污染全局 context。未提供 getter 时，桥接层在加载前校验已有 `getAppContext().sessionKey`。若页面仍有其他活跃桥接实例，待挂载实例的代次还须与它们一致；不一致时即使 getter 返回自身代次，也不得覆盖全局 context。会话不匹配或受控值非 `undefined`/`null`/非空字符串按 MFU-017 显示可操作诊断并停止加载；getter 抛错、返回非对象或 thenable 归 MFU-016（`phase: 'getContext'`）。`sessionKey` 为 `null` 时不执行 getContext、provideAppContext、loadRemote 或自动重试。加载尝试作废后不得调用 provideAppContext，也不得让迟到的旧尝试覆盖新会话。

### 4.4 错误边界与跨 root 的真相

- 宿主侧占位覆盖**加载阶段与首次根提交前的挂载阶段**错误（远程不可达、契约非法、mount 抛错/拒绝、首次渲染失败）；首次根提交后由子应用自己的错误边界处理。
- 子应用挂载后是其自己的框架 root：**宿主的 ErrorBoundary（React）或 errorCaptured（Vue）捕不到跨 root 的子应用内部渲染错误**。子应用内部错误处理是子应用自己的事（可自建 ErrorBoundary/onErrorCaptured）；首次提交探针只负责挂载阶段，不自动兜底运行期所有错误。README 禁止宣称"宿主兜底子应用一切错误"。
- loadRemote 的 MFU 错误保留 code/cause 原样透传到占位，不统一包成 UNKNOWN。
- 默认加载/挂载错误占位沿用 5.2.2 的两条恢复操作：「重试加载」只重建本次尝试；「刷新页面重试」仅由用户点击触发，保留当前地址。生产静态子依赖 chunk 失败属于浏览器 module map 缓存边界，允许同页重试仍失败，必须验证产品刷新按钮确实恢复；自定义错误占位完全接管展示与操作，文档要明确由调用方实现恢复入口。

### 4.5 多实例与守卫

- **DOM 所有权**：宿主包装组件只创建并保持稳定的空挂载 `el`；从调用 `mount` 到 `unmount` 完成，`el` 内部节点只由子应用框架管理。pending/error 占位放在挂载容器的兄弟节点或外层，不让宿主 Vue/React 的重渲染去 patch 远程 root 内部。加载成功移除占位时不得销毁该 `el`。宿主组件卸载时先通知契约清理，再释放容器。
- **宿主缓存边界**：Vue `<KeepAlive>` 的 deactivate 不是组件卸载，不能声称此时自动执行 `unmount`；缓存页面中的子应用继续保有 root 与状态。v1 不新增跨框架暂停/恢复生命周期；需要离页即销毁时，宿主不要缓存该桥接页。登出即使页面被缓存，受控 `sessionKey: null` 仍须在下一次该包装组件收到更新时清理；鉴权退出流程应同时移除或禁用缓存的私有页面，不能等用户再次进入才清理。
- 同一 spec 的桥接组件多实例并存：契约按 el 分键，互不干扰（BR 用例）。
- `AppContext` 是页面级全局单例，同页多桥接实例必须使用同一当前会话；不承诺同页同时承载 A/B 两个不同账号。实例的 `sessionKey` 与全局会话不一致时按 MFU-017 拒绝挂载，不能让两个实例互相覆盖身份数据。
- 同一容器未卸载再次 mount：拒绝并按 MFU-016（`phase: 'mount'`）给出中文根因（容器已被占用）与修法。
- React 宿主 StrictMode 双 effect（mount→cleanup→mount）安全：顺序 unmount/mount 不得产生双实例或残留；不得用"禁用 StrictMode"换通过。
- 旧请求还停在 loadRemote、尚未取得契约时，卸载或换代也必须使该请求失效；迟到结果不得调用 `mount`。已经开始 mount 的迟到 resolve/reject 不得复活已卸载实例、覆盖新代次或产生未处理拒绝；BR/BN 分别用真实延迟请求验证。
- 已进入 `loadRemote` 的旧请求可能在返回桥接层前执行远程 `onSession`；桥接层不能声称取消了这段运行时工作。旧会话的 `onSession` 必须遵循现有 `signal.aborted` 契约，在异步等待后、写私有状态前检查信号；换账号用真实延迟 `onSession` 注入验证，报告分别记录运行时会话状态、全局 AppContext 与子应用 DOM。

## 5. 运行时、导入图与开发态

### 5.1 内核与导入图

- `dist/runtime.js` 内核**零改动**为首选目标；桥接层经注入 loadRemote 工作（与两个既有适配器同模式），不初始化第二份内核。若实测存在必须修内核的缺陷，修复与 Vue/React 回归成套，不承诺"内核零改动"绑死。

### 5.2 dev 引擎接线（必做项）

- `virtual.ts` 的 dev 门面生成：`/runtime` 与 `/react` 两个导出面各加入 `defineBridgeApp`，dev 下远程源码从各自入口导入可用，不回退 any、不初始化第二内核。

### 5.3 dev 类型

`./bridge` expose 的 `.ts`/`.tsx` 走现有 dts 双轨：可达 fsRoot 出精确契约类型；源码不可达或 `devFsRoot:false` 时出可解析的宽松声明。宿主泛型 `P` 只约束调用方显式提供的 props；不能承诺 `createVueBridgeApp('remote/bridge')` 自动从字符串 spec 推断远程 props，也不能把宽松轨说成编译期校验通过。两子应用入口的 d.ts 必须准确导出各自 `defineBridgeApp` 签名。

### 5.4 错误码登记

桥接错误码放在桥接层自己的码表（如 `src/bridge-errors.ts`），复用现有 `FgError` 类型，不把桥接专用逻辑塞进 `runtime.js`。登记 MFU-015/016/017，MFU-016 的 `details.phase` 明确 getContext/mount/unmount；扩展 `scripts/check-manual-codes.mjs` 的源码扫描范围，并同步 `src/diagnostics.ts`、README 中英错误码表与占位文案。若实施当天号码已占用，整体顺延并同步测试，不能复用语义不同的旧码。
