## 3. P1：同一个 React 实例没有跟随 sessionKey 切换

### 3.1 问题位置与证据

文件：`packages/plugin/src/react-adapter.ts`。

- `RemoteLoader` 的 effect 依赖只有 `attempt`，没有观察当前会话代次。
- `createUseLoadRemote` 的 effect 依赖 spec、部分 options 和 loadRemote，没有当前 sessionKey。
- `createReactHostPages` 只在再次调用 `component(spec)` 时检查会话并清组件缓存。
- 示例把 `component(spec)` 返回值存成模块级常量。A→B 时宿主可能只 rerender，不重新调用 component，因此缓存逻辑不能解决已挂载组件的问题。
- 现有退出再登录 fixture 会卸载再挂载组件，可能掩盖同实例问题。

复核使用真实构建适配器、JSDOM 与 React 测试工具，在 session A 加载后，把 context 改为 B 并重渲染同实例，得到：

```json
{"case":"same mounted hook A -> B","calls":["A"],"rendered":"2:A"}
{"case":"same mounted remoteComponent A -> B","calls":["A"],"rendered":"loaded-for:A"}
```

这证明适配层没有再次加载当前会话。不是说所有项目都会显示旧用户，而是插件当前不能保证原任务书要求的同实例会话更新。

### 3.2 必须实现的行为

1. 宿主提供新 context，并触发 React rerender 后，已挂载的 hook、remoteComponent、hostPages 页面要观察新的有效 sessionKey。
2. 新会话加载走当前 context 的生命周期，不能沿用旧会话的适配器数据或组件本地私有状态。成功模块 namespace 可以复用；其中应用自己维护的用户 store，由它的 onSession/退出清理逻辑更新，插件负责正确调用和阻止过期适配器结果。
3. A 的慢请求晚于 B 返回时，不得覆盖 B。退出时由宿主先 clearAppContext 再卸下鉴权内容；插件不猜哪些组件受保护，也不扫描清空应用任意 store。远程异步业务要按会话 signal/代次防止把 A 的数据写进 B。
4. 同一会话普通 rerender 不得重复触发生命周期、重置组件或无限请求。
5. setup 保持应用初始化语义；onSession 按会话代次执行。会话切换不应重新执行成功模块代码或制造 React 第二实例。
6. 不把 context 的普通对象读写宣称成自动响应式订阅。文档写清宿主需要在状态变化后触发渲染；使用现有公共 API。
7. 不破坏 Vue KeepAlive 的既有退出行为。React 修复不能把 Vue 的缓存清理时机顺手改掉。

补充边界：没有配置 setup、没有提供 context/sessionKey 的公开组件也必须正常加载，不能为了修复会话问题强制所有用户登录。测试分别包含“始终无 session 的公开组件”和“有 A/B session 的受保护页面”。`undefined→A`、`A→B`、`A→clear→B` 分开验证；退出后的受保护页由宿主卸载。已有有效 sessionKey 的普通 rerender 不应重置状态。

宿主应在登录/换账号动作中先提供新的 context，再更新 React 状态触发 rerender。beforeLoad 是每次实际加载前同步最新 context 的入口，不能只把新账号藏在 beforeLoad 中，再期待一个尚未发生的重新加载自动发现它。示例必须把这条数据流写清，不要求用户手动改 key 或每次 render 新建组件工厂来绕过插件缺陷。

### 3.3 必测用例

- 同一个 `useLoadRemote` 组件 A→B，spec 和其他 options 不变。
- 同一个 `remoteComponent` A→B，不依赖卸载重建。
- 模块级缓存的 `hostPages.component(spec)` 页面 A→B。
- 退出清 context、随后 B 登录；远程测试 store 记录实际用户 ID，而不是只显示宿主 Provider 的用户名。
- 故意延迟 A 加载，让 B 先成功，再释放 A；B 保持不变。
- 同一会话重复 rerender，加载与 onSession 次数符合契约。
- React 18、19 与 StrictMode；用真实浏览器补一组身份切换测试。

### 3.4 顺带核对 reload 清理

hook 的 effect cleanup 设置局部 cancelled，但 reload 使用 reqGen。核对 reload 中卸载、session 切换和乱序请求的失效条件：过期结果不能写入当前状态，不能仅以“React 没打印 warning”作为通过证据。增加实际状态/调用计数断言。

本轮统一 hook 状态契约：首次加载、spec/有效选项/会话变化、显式 reload，均进入 `data=undefined、error=undefined、loading=true`；当前尝试成功后写 data，失败后写 error，二者都令 loading=false。过期尝试不修改三者。reload 返回 Promise<void>，失败呈现在 error，不向按钮调用方产生未处理拒绝。同步类型注释、双语文档和测试；不要新增“保留旧会话数据”的选项来回避清理。

## 4. P1：tsconfig paths 的判断会误判精确类型轨

### 4.1 问题位置与证据

文件：`packages/plugin/src/dts.ts`，`hostPathsCovers()`。

当前扫描根目录所有 tsconfig 文件，并在解析前用正则查文本。注释中的 paths、其他配置块里的同名键、无关 tsconfig.node.json 都可能让它返回 true。单独的 `"r"` 键也不能自动证明 `r/Button` 已被覆盖。

复核给无关 `tsconfig.node.json` 放了如下合法 JSONC：

```jsonc
{ "compilerOptions": { /* "r/*": ["types/r.d/*"] */ } }
```

实际类型生成结果：

```json
{"case":"commented paths in unrelated tsconfig","ambientGenerated":false,"preciseGenerated":true}
```

用户没有有效 paths，却被当成启用了精确轨，必要声明被抑制。

### 4.2 修复要求

- 使用有效 JSONC 配置解析，不用原始文本匹配代替语义。
- 明确宿主实际应用 tsconfig 的选择、extends 和 references 处理规则；不能“任意一个 tsconfig 有路径就全局启用”。
- 检查对应模块路径的实际覆盖关系及目标，不只检查键名出现。
- 多个 TS 上下文并存时，不得让 node 配置影响浏览器应用导入。
- 不静默修改用户 tsconfig。若需要明确配置选择，尽量沿用现有工程配置，确需公共选项时说明原因、默认值和迁移影响，不堆兼容 API。
- 保留精确轨与零配置可解析轨的真实能力；不能通过全部改 any 来“修复”。

实现不要求你重写一套 TypeScript 解析器。先复用已有可用的配置解析能力；需要新增依赖时说明具体缺口及打包影响。继承配置里的相对路径必须按其声明文件解析。配置无效或无法唯一确定应用上下文时，给出能修正的中文诊断和实际降级规则，不能悄悄删掉 ambient 后让导入失效。修复也不能静默改变现有 shim 模式的公开合同。

### 4.3 验收

真实生成输出后使用有效 tsconfig 运行 tsc：注释路径、无关 node 配置、只有 exact 键、有效 wildcard、extends 继承、错误目标、合法参数与错误参数分别验证。有效精确轨应获得真实类型；未配置路径的默认轨应能导入；IDE 和命令行采用的配置契约一致且文档明确。

## 5. P1：降级为 any 后保留失效的源码转发文件

### 5.1 问题位置与证据

### 5.2 修复和验收

1. 明确每个远程的插件自有生成文件及所有权，只清理自有输出，不能删除用户类型文件或其他远程目录。
2. source→无 fsRoot、source→源码不可访问、source→shim/any，都不能留下失效的源码 import。
3. 宿主已有 paths 指向精确目录时，降级后的实际解析也应按已声明契约可用，不能要求用户每次手动删 paths 才恢复。
4. 恢复源码后能重建精确轨，并真实拒绝错误 props/参数。
5. exposes 删除、远程移除、配置切换要核对旧输出。`dts:false` 的停止生成/旧输出处理规则写明，不擅自扩大删除范围。
6. 在同一输出目录连续做“精确→降级→恢复”，每一步真实运行 tsc。禁止每一步先删光工程，使残留问题消失。

这里不要求实现远程文件系统实时监听。若现有合同规定重启宿主 dev 后重新生成，测试可在同一工程/输出目录重启生成；保留中间输出和编译结果即可。`dts:false` 至少在干净目录不生成，切换后的旧文件策略写明并测试；不授权删除用户自己写的声明。

manifest 整体不可达与“manifest 可读但不含 fsRoot”是两种不同情况。前者不能凭空猜 exposes；可以沿用已声明的缓存策略或报告无法更新，但不得把保留的过期精确类型宣称成新的成功降级。任务书中的 any 可用要求主要针对已知公开 exposes、源码不可用的场景。

## 6. P1：生产重试把第二次成功加载也改成新模块 URL

### 6.1 问题位置与证据

文件：`packages/plugin/src/index.ts` 的 generateBundle 中 remoteEntry 重写。

当前 `__fgR` 只计调用次数，没有判断前一次是否失败。从第二次调用起追加 `fulgurjs_retry`。提取当前 helper 连续调用得到：

```json
["./assets/Context.js","./assets/Context.js?fulgurjs_retry=1","./assets/Context.js?fulgurjs_retry=2"]
```

这是已确认的 helper 行为。完整浏览器影响还需要新增用例验证：两个 expose 别名指向同一个源码/chunk 时，可能通过不同 loadRemote 缓存键触发第二次导入，导致模块重复求值、Context 或 store 身份分裂。

### 6.2 正确契约

- 只有确实失败、需要恢复的加载尝试才改变请求 URL。
- 成功模块重复访问保持缓存和对象身份。
- 同一资源并发请求复用正确的进行中状态，不产生多个成功实例。
- 失败后恢复不是永久缓存 rejected Promise；也不是每次成功都 cache bust。
- 保留构建器对依赖、CSS、预加载、base 和子路径的正确处理。避免无差别正则改写所有 import 后宣称完整支持。
- 联合核对 runtime importEntry、dev expose loader、prod loader：已有 query、hash、非根 base、跨源 URL 的拼接正确。
- “失败根 chunk 能恢复”和“失败的是它的静态子依赖能恢复”分开测；不能用前者证明所有失败缓存都被穿透。

不要把 helper 字符串输出当完整浏览器复现。先建立两个 expose 指向同一源码的真实构建，测 namespace/Context 身份与执行次数。如果构建器把两个 alias 合并成只调用一次 loader，该场景无法触发时继续寻找实际可达路径，原样记录；不能篡改浏览器结果来迎合本文推断。

重试不得通过给 React、共享 Context 或所有成功依赖统一加随机 query 来实现。保留容器 CSS 预加载和构建依赖关系。若静态子依赖失败暂时无法在同页恢复，标出具体失败 URL、缓存位置和缺少的行为；它会使对应恢复项未通过，不能写成“所有故障恢复已完成”，也不能贸然递归改写整个站点依赖图。

### 6.3 必测

1. 同一源码暴露两个别名，导出对象/React Context，生产浏览器先加载别名一再别名二：对象严格相等、模块执行计数一次、成功后零多余 retry URL。
2. 并发打开相同模块；重复打开已成功页面；保持 singleton 和会话生命周期。
3. 首次实际网络失败→解除阻断→用户点击重试→加载成功；保留第一次失败请求、恢复请求和截图。
4. 分别阻断 entry、expose chunk、静态依赖；记录支持范围及真实结果，核心页面恢复要求不能用备注替代。
5. dev、生产子路径和含 query 地址。修复后回归 Vue，不只测 React。
