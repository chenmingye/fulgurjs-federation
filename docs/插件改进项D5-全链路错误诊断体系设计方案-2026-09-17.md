# D.5 设计方案：全链路错误诊断体系（错误提示全面化）

> 状态：**已实施**（错误码体系 CFG/DEV/BLD/MFU/CC 五段 + 三段式报错 + 故障注入矩阵 F1~F14，见 README 错误码总表与「配置出错？报错看得懂」节）。
> 需求来源：用户反馈「错误提示还是不够全面……这个配置相对抽象，任何环节都可能出问题，
> 要详细指出错误在哪里」。本方案把"任何环节出错都有明确指引"作为插件的正式能力项（H9
> 「出错能懂」的全面化落地）。
> 起草：2026-09-17。

---

## 1. 问题：为什么现在的报错不够

联邦配置是**分布式**的：一份配置横跨宿主/远程两个应用的 vite.config、远程 exposes 表、
宿主路由表、运行时协商，失败点分布在配置期 → dev 启动期 → 构建期 → 运行时加载链的
每个环节。现状三类缺陷：

1. **覆盖不全**：运行时仅 MFU-001~008 八个码；配置期 options.ts 有 12 处 configError；
   而 dev 启动期（remote 不可达、optimizeDeps 矛盾、origin 错位、缓存漂移）、构建期
   （expose 解析、TLA）、运行时（组件缺 default 导出、CORS 归因）大量环节静默或只有
   浏览器原始报错。本项目历史事故中至少 5 类当时无插件级提示，靠 40 分钟级二分定位
   （dayjs 双重 interop、avue UMD 预构建内联、静态导入虚拟模块、server.origin 错位、
   immutable 缓存致门面 404）。
2. **格式不统一**：有的三段式（D.1），有的单行（configError），有的只有浏览器原生
   报错（网络失败）。
3. **缺上下文**：报错不附带"当时的状态"（注册了哪些 remote、shared 协商到了什么版本、
   请求的完整 URL 与响应码），用户要自己开 DevTools 拼线索。

## 2. 目标与非目标

**目标**
- G1 全链路失败点清单化：生命周期 6 个阶段 × 每阶段全部可失败环节，逐一映射到错误码
  与三段式文案（见 §5 清单，共 24 项）；
- G2 统一错误格式与分段错误码体系（兼容现有 MFU-0xx）；
- G3 错误附上下文快照（注册表/协商结果/请求详情），开箱即懂；
- G4 每个错误码有对应的**故障注入自动化用例**（H9 口径：断言错误码 + 文案要点）；
- G5 错误码与手册 §8 排查表一一对应（报错里直接给手册锚点）。

**非目标**
- 不覆盖宿主/远程应用自身的业务错误（如后台接口 401）；
- 不做自动修复（只指路不代改，H3 显式原则）;
- 不覆盖 vite/rollup 上游自身的崩溃（如 V8 栈溢出），但提供"已知上游问题"排查表条目。

## 3. 设计原则

1. **三段式强制**：现象（什么操作、什么对象、什么结果）→ 根因（最可能的机制，附证据
   数据）→ 修法（具体到配置键/文件/命令）。所有 ERROR 级报错必须三段齐全，文案模板
   化（函数生成，禁止散落字符串拼接）。
2. **错误码分段**（兼容现有 MFU 运行时段）：
   - `MFU-0xx` 运行时加载/协商（001~008 保留，新增 009+）；
   - `CFG-0xx` 配置期（normalizeOptions，把现有 12 处 configError 逐步编入码表）；
   - `DEV-0xx` dev 启动/模块转换期（D.1 检测归入此段，追溯改码为 DEV-001 并保留
     旧文案兼容）；
   - `BLD-0xx` 构建期。
3. **上下文快照随行**：ERROR 报错附 `details`（FulgurjsError 已有 details 字段，现状利用
   不足）——remote 名、尝试的完整 URL、HTTP 状态码、exposes 清单摘录、shared 协商
   结果（版本+提供方）、插件版本（D.3 的 runtime version）。同时写入
   `window.__FULGURJS_INFO__.errors`（已有 errors 数组，扩展结构化字段）。
4. **通道矩阵**（同一错误多处可见，格式一致）：
   | 通道 | 内容 |
   |---|---|
   | dev overlay / build 失败 | CFG/DEV/BLD 段（配置与编译期） |
   | console.error（格式化多行） | 全部（运行时段主通道） |
   | `fulgurjs:error` CustomEvent（已有） | 运行时段，附带结构化 details |
   | 宿主 errorComponent（已有） | 页面级加载失败，标题带错误码 |
   | 手册 §8 排查表 | 每码一节：现象/根因/修法/注入用例编号 |

## 4. 错误信息标准格式

```
[fulgurjs:CODE] 一句话现象。
根因：…（机制解释 + 关键证据值，如 URL/状态码/版本协商结果）。
修法：…（具体配置键 / 文件 / 命令）。
详见手册 §8「CODE」；上下文：{...关键快照字段...}
```

约束：单条报错 ≤15 行；修法必须可执行（给出键名或命令，不说"检查配置"这种空话）；
同屏多错聚合输出（各自带码），不刷屏不吞错。

## 6. 实现要点

1. **码表即代码**：`ErrorCodes` 常量表扩展四段（CFG/DEV/BLD/MFU），每项带
   `{ code, stage, title, doc }` 元数据；手册 §8 由该表生成（脚本产出，杜绝文档漂移
   ——此前手册/注释对不上 5 处的教训）。
2. **文案生成器**：`formatFulgurjsError({ code, symptom, cause, fix, details })` 统一
   三段式输出，禁止散落拼接；ERROR 级强制 cause/fix 非空（单测断言）。
3. **dev 中间件**：facade 404 拦截（#13）在宿主 dev server 加一个 404 拦截中间件，
   响应体即三段式指引（浏览器 Network 里直接可见，不用翻 console）。
4. **上下文快照**：`window.__FULGURJS_INFO__.errors` 扩展为
   `{ code, message, details, time, spec?, remote? }[]`（环形缓冲，上限 50 条）。
5. **兼容**：MFU-001~008 码值不变（手册/既有测试不破坏）；D.1 的文案追加 DEV-008 码前缀。

## 7. 测试验证计划（H9 口径：每码一个故障注入用例）

- **单测**：码表完整性（每码有 title/doc/文案非空）；文案生成器三段齐全；
  R 级注入类（DEV-003/004/005）用构造的 vite 配置对象断言告警文本。
- **fixtures 故障注入矩阵（dev+prod 双环境）**：每个 MFU 码一个 spec 用例——拔
  remoteEntry（001）、改自报名（002）、strictVersion 冲突（003）、import:false 缺失（004）、
  重复 init（005）、错 expose 键（006）、断预载（007）、未注册远程（008）、无 default
  组件（009 新增）、双版本 runtime（010 新增，构造双打包副本）。断言：错误码出现 +
  文案含根因关键词 + `__FULGURJS_INFO__.errors` 有结构化记录。
- **testbed 真实注入（dev+prod+NGINX 全实测）**：未清 .vite 触发 DEV-009（404 指引
  响应截图）；拔掉某 remote dev server 触发 DEV-001（启动期报错截图）；故意写错
  remotes 端口触发 DEV-005。三组截图+文本归档 docs/screenshots/。
- **验收**：24 项清单每项有码、有用例、手册 §8 可检索；全量既有测试（106 单测 +
  fixtures dev 10/prod 8 + H7）不回归。
