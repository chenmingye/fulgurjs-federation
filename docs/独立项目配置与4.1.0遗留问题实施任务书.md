## 1. 为什么要改：现状与可核实的偏差

当前 `testbed/mes-zc/fulgurjs.config.ts` 位于三个应用的共同父目录，顶层是 `root + apps[]`，在一份文件里声明 admin、BPM、lowcode 三个应用。三个 `vite.config.ts` 都以 `../fulgurjs.config.ts` 读取它，再调用 `federationOptionsForApp(repo, app)`。这在同一个测试工作副本里能运行，却让一个单独部署或位于其他仓库的远程项目必须知道宿主项目的目录、页面表与其他远程配置。Webpack Module Federation 的核心模型是多个**独立构建**协作，不要求它们共享一份物理配置文件；本项目的新手主路径也应符合这个模型。参考 [Webpack 官方概念说明](https://webpack.js.org/concepts/module-federation/) 中 separate builds / containers 的定义。

## 2. 产品决策：默认每项目一份，旧聚合配置保留兼容

### 2.1 推荐的文件位置与归属

每个应用根目录各放一个 `fulgurjs.config.ts`：

```text
cku-mes-admin/fulgurjs.config.ts       # 只描述 admin 自己的 federation 选项，以及宿主页面核对所需数据
cku-mes-bpm/fulgurjs.config.ts         # 只描述 BPM 自己的 exposes、setup、shared、反向消费 admin 的地址
cku-mes-lowcode/fulgurjs.config.ts     # 只描述 lowcode 自己的 exposes、setup、shared
```

它们**不应**通过 `../fulgurjs.config.ts`、`../cku-mes-xxx` 或跨仓库源码导入来构建。宿主需要知道远程的公开容器名和 dev/prod 地址，这是正常的消费方配置；远程需要知道自己暴露什么、如何初始化，反向消费宿主时才需要宿主地址。任何一方都不需要知道对方的源码绝对路径、共同父目录或 `apps[]` 列表。各自的 Vite `base`、dev 端口、代理和其他插件继续由各自 `vite.config.ts` 管理；不要为了 `explain` 又把这些值复制进第二套配置。同一 monorepo 中的应用也各自持有配置；普通小应用仍可直接调用 `federation({...})`，不强制为用插件而新建配置文件。

这里的“一项目一份”是**默认接入体验**，不是禁止 monorepo。现有 `defineRepoConfig`、`loadRepoConfig`、`federationOptionsForApp` 和 4.1.0 的 `federation({...})` 保留一段兼容期；已使用聚合配置的项目不应因升级立即报错。README 首屏与 `fulgurjs init` 默认模板改为单项目用法，monorepo 聚合方式放进高级/迁移章节，并清晰标明两种模式。**兼容不等于推荐**：不能把三层转换继续写成所有项目的主入口，也不能让本轮迁移后的三个 MES 项目继续使用它。

### 2.2 默认 API：配置直接就是插件选项，Vite 只调用一次插件

**本轮默认接法固定为下例的形态。** 一个项目的 `fulgurjs.config.ts` 默认导出**直接可传给 `federation()` 的选项对象**，不再包 `federation: { ... }`、`apps[]`、`root`、`host/remote` 角色壳，也不需要 `defineAppConfig()` 运行时函数。TypeScript 用 `satisfies FederationOptions` 做编译期形状检查；若当前公开类型没有从主包导出，执行者补齐类型导出。该配置不执行异步加载。Vite 里只导入一个本项目常量，写一次 `federation(fulgurjsConfig)`；使用者可直接看到插件入口、配置文件位置和配置内容。各项目其余 Vite 插件、`base`、server、代理、构建选项继续留在原 `vite.config.ts`。

```ts
// cku-mes-bpm/fulgurjs.config.ts —— 本项目自己的配置；以下键均直接属于 federation 选项
import type { FederationOptions } from '@fulgurjs/federation'

export default {
  name: 'mes-bpm',
  exposes: {
    './pages/bpm/task/todo': './src/views/bpm/task/todo/index.vue',
    './TaskCard': './src/fulgurjs/exposes/TaskCard.vue',
  },
  setup: './src/fulgurjs/setup.ts',
  // BPM 确实反向消费 admin 时才写；这里配置的是地址，不依赖 admin 的源码目录
  remotes: { 'cku-mes-admin': { dev: 'http://localhost:8773/main', prod: '/main' } },
  shared: {
    vue: { singleton: true, requiredVersion: '^3.4.0' },
    'vue-router': { singleton: true, requiredVersion: '^4.4.5' },
    pinia: { singleton: true, requiredVersion: '^2.1.7' },
  },
} satisfies FederationOptions

// cku-mes-bpm/vite.config.ts —— 只展示联邦相关行，原有 Vite 配置原样保留
import federation from '@fulgurjs/federation'
import fulgurjsConfig from './fulgurjs.config'

// plugins: [原有插件, federation(fulgurjsConfig), 原有插件]
```

上面的 URL 和 shared 版本仅示范对象结构；迁移 MES 时必须以**当时现有有效配置**为准，不能复制示例覆盖实际值。宿主同样只把本应用的 `name/remotes/exposes/setup/shared` 写进默认导出；宿主页面核对数据另以**命名导出**提供给 CLI（见 §3），Vite 只消费默认导出，避免把 `pages` 等非插件字段误传给 `federation()`。普通小应用也可直接在 `vite.config.ts` 写 `federation({ name, ... })`，无需创建配置文件。

**简洁性是验收条件，不是示意图。** 最终三份 MES `vite.config.ts` 不得再出现 `loadRepoConfig`、`federationOptionsForApp`、`fileURLToPath(new URL(...))`、父目录配置路径、按字符串查找自身应用名，也不得出现 `federation(appConfig.federation)` 等额外包装。CLI 内部可以有加载/校验流程，但不能要求应用开发者在 Vite 入口手动串联。若执行者认为一行接入需要换 API 名称，应先在报告中给出**同等简洁且可运行**的三项目代码和取舍；不得自行退回三层套函数。

### 2.3 配置加载器的关键约束

当前 `loadRepoConfig()` 会把 TS 配置源码复制到系统临时目录再 import。**这一点与单项目配置导入本项目的 `pages.data.ts` 不兼容**：相对导入会以临时目录为基准而失效。新的 CLI 配置加载路径必须以原配置文件为解析基准，读取默认导出的插件选项与可选的页面数据命名导出；支持本项目内相对导入的纯 TS/JS 数据模块，兼容 Node 18 与仓库现有 Node/ESM/CJS 测试矩阵。可以采用仓库已有构建工具或可控的临时 bundle，但不能引入“只在本机 Node 24 能跑”的隐含要求，不能执行宿主浏览器入口或加载 Vue 页面来读取页面清单。临时文件要按任务独立目录清理，不写入业务源码。**这个加载器供 CLI 内部使用，不应出现在项目 Vite 接入代码里。**

额外约束：配置文件路径缺失、导入失败、字段冲突、无 `name`、expose 路径不在当前项目等情况给出项目路径/字段/修法；配置加载不得输出 token、内网凭证或环境变量秘密。运行时与 CLI 解析同一份配置值，dev/prod 的 URL 选择规则保持 4.1.0 语义。

## 3. 宿主页面表只能有一个真实来源

将 admin 的 26 条路由记录（覆盖 27 个菜单入口）移到浏览器与 Node/CLI 都能读取的**纯数据模块**，例如 `src/fulgurjs/host/pages.data.ts`。该模块只导出数据与纯 `deriveSpec`/前缀映射；不要导入 Vue、Pinia、`remoteSchema`、宿主桥或浏览器全局对象。宿主 `pages.ts` 的 `createHostPages`、静态路由和布局仍从这个数据模块得到页面列表；宿主自己的 `fulgurjs.config.ts` 也引用**同一个数据模块**，供 `explain` 和 `check-pages` 使用。不得再在配置中手写第二份 26 条清单。

推荐形态：

```ts
// cku-mes-admin/src/fulgurjs/host/pages.data.ts（唯一手工维护位置）
export const remotePrefixes = { '/flowable/': 'mes-bpm', '/lowcode/': 'mes-lowcode' }
export const deriveSpec = (route: string) =>
  'pages/' + route.replace(/^\/(flowable|lowcode)\//, '').split('/').filter((seg) => !seg.startsWith(':')).join('/')
export const pages = [
  { route: '/flowable/bpm/task/todo', name: 'BpmTodoTask', title: '待办任务' },
  { route: '/flowable/bpm/manager/model/:type/:id', name: 'BpmModelUpdate', spec: 'pages/bpm/manager/model/update', title: '修改流程' },
  // ...其余条目只在此处维护
]

// cku-mes-admin/fulgurjs.config.ts
import { pages, remotePrefixes, deriveSpec } from './src/fulgurjs/host/pages.data'
import type { FederationOptions } from '@fulgurjs/federation'

export default {
  name: 'cku-mes-admin',
  remotes: { 'mes-bpm': { dev: 'http://localhost:4529/flowable', prod: '/flowable' } },
  // 自身 exposes/shared 等按当前真实配置保留
} satisfies FederationOptions

// 仅 CLI explain/check-pages 读取；不是 federation() 的参数
export const hostPages = { pages, remotePrefixes, deriveSpec }

// cku-mes-admin/src/fulgurjs/host/pages.ts
import { pages, remotePrefixes, deriveSpec } from './pages.data'
export const hostPages = createHostPages({ pages, remotePrefixes, deriveSpec, schema: remoteSchema, beforeLoad: fulgurjsBridge, base: import.meta.env.BASE_URL })
```

上例的 `deriveSpec` 取自当前 MES 路径规则；执行者须用现有 26 条数据逐项核对结果，保留带参数路由的显式 `spec`，不能只凭示例推断所有页面都适用。`hostPages` 命名导出只是给 CLI 的数据读取约定，不是开发者在 Vite 中再调用一次的函数，也不是第二份路由数组。CLI 必须清楚报告它是否找到这个导出；没有宿主页面表的纯远程配置不应因此报错。若实际实现选择另一命名方式，仍必须保持“默认导出直接传插件、页面数据只维护一份、浏览器不加载 Node 配置代码”的行为。

`check-pages` 应检查这个**运行时同源的页面数据**，与远程的**发布后 manifest** 对比：

- 宿主配置只需知道 remote 名与地址，不必在 `apps[]` 中列出远程项目；远程可在任意仓库或服务器。
- 支持明确指定 manifest：例如 `--manifest mes-bpm=/absolute/path/fulgurjs-manifest.json` 或 `--manifest mes-bpm=https://.../fulgurjs-manifest.json`；已有 `--site` 可按宿主远程的 prod URL 推导同站部署地址。不能把“有同仓本地 dist”作为唯一正常路径。
- 对 `remotePrefixes` 未注册、路由遮蔽、重复 name/spec、manifest 确认缺 expose 报确定错误并退出非零；远程不可达标为“无法验证”，`--require-verified` 等 CI 严格模式也要非零，避免 0 条核对却显示通过。输出每个 remote 的 manifest 实际来源，防止使用了旧本地 dist 而误以为在查 8662。
- `--site` 或显式 manifest URL 指向部署站点时，应优先使用该指定来源；若还查本地产物，必须清楚显示优先级与最终选择，不能悄悄以本地旧产物替代线上验证。

## 4. 其他遗留问题的处理要求

### 4.1 公开文档与 CLI 不再描述不存在的自动生成

**这是本轮独立交付项，不是改几句首页简介。** 以执行时实际准备发布的 `packages/plugin/package.json`、源码导出、CLI 行为、已发布 npm 包内容为基线，逐段核对仓库根 `README.md`、构建复制到 `packages/plugin/README.md` 且真正进入 npm 包的 README、`docs/迁移指南.md`、公开示例、CLI `--help`、`init` 输出、MES 项目侧 README 与旧实施方案。建立一份“旧文案位置 → 实际代码/公开类型证据 → 修改结果”的核对表，至少覆盖安装版本、包 exports/导入路径、默认接入代码、配置文件位置、CLI 参数及输出、`setup/onSession` 时序、普通 TS expose 的消费、Vue 组件消费、页面适配器、shared 与 dev/prod 默认值、预载、缓存、类型生成与部署。所有拷贝即用代码块要能以目标正式包安装后运行或通过类型检查；不能把旧版本号、已移除子路径或历史兼容 API 写成当前主路径。

**已发现的具体过时项必须逐条修正：** README §“单配置驱动 Vite”把 `loadRepoConfig + federationOptionsForApp + federation` 作为推荐写法；§“fulgurjs.config.ts”以 `root + apps[]` 聚合配置为默认；§“CLI”也推荐粘贴块或转换器；§9.1 声称 `host.prefetch` 可写在配置里且 `init` 会生成 `bridge.ts`，并让用户删桥重跑 `init`。当前插件 `HostConfig` 无 `prefetch`，当前 `init` 不生成桥/路由/远程 setup/NGINX 实际文件。这些章节应按 §2 的单项目简明主路径、实际 CLI 行为与真正可配置项重写，并相互链接，避免首页正确而后文冲突。`init` 默认只生成**当前项目自己的配置起步模板**；如仍输出 NGINX 示例，应称“打印样板”。若要将预载做成新的真实配置能力，须完整实现类型、应用接线与测试，不能只保留文案。

将旧方案 §11 标为“4.0.0 历史链路”，写明当前链路已使用 `setup/onSession`，不要再称旧 `federatedBoot` 手动链路为当前代码；MES 源码里的 `[fulgurjs:init] generated` 等标记要核实来源后修正，不能让人误以为 CLI 能重建这些手工业务文件。README 首页以“每项目一份配置 + `federation(fulgurjsConfig)`”为默认示例，普通 TS expose、普通 Vue 组件、带 setup 的远程页面仍要各有可运行示例。说明 `setup` 是**远程应用级配置**：该远程任意业务模块的 `loadRemote` 都会经过它；若不需要初始化，不配置它。旧聚合配置与旧手动链路只在明确标记的“历史兼容/迁移”章节解释；CHANGELOG 保留版本演进史，README 主体描述当前可用状态。发布后检查 npm 包内 README 与源码导出一致，不只看 Git 仓库根文件。

### 4.2 `explain` 准确报告角色与数据来源

### 4.6 修复 8662 BPM 审批详情页的标签栏位置，并核对联邦样式入口

**用户所见与目标。** 用户给出的 8662 截图里，流程实例详情的标题、表单、右侧审批时间线在最上方，而“审批详情 / 流程图 / 流转记录”标签栏出现在长空白之后、接近视口底部；乾坤版标签栏在上方。目标是进入同一流程实例时，标签栏位于标题行之下、各标签内容之上；默认显示“审批详情”，表单与右侧时间线位于这个标签的内容区。内容为空时也不能用一个视口高度的空白把标签栏推下去。切换“流程图”“流转记录”后标签栏仍在同一上方位置，滚动区和操作按钮正常。

截图证据已随文档保存为 [8662 审批详情标签栏沉底截图](screenshots/8662-bpm-approval-tabs-bottom-20260925.png)，供执行者比对；它只证明可见现象，不代替浏览器计算样式证据。

**已核实的代码机制，作为排查起点。** `cku-mes-bpm/src/views/bpm/processInstance/detail/index.vue` 第 43 行的 `<el-tabs>` 没有指定底部位置；本地安装的 Element Plus 2.9.1 的 Tabs 实现却按 `[panels, header]` 顺序生成 DOM，顶部模式靠主题 CSS 中 `.el-tabs--top { flex-direction: column-reverse }` 把 header 显示到上方。若这条主题样式没加载、加载迟于页面渲染或被覆盖，header 就会按 DOM 顺序落在内容后。该详情页的 `.form-scroll-area` 又按视口计算较大的高度，因而会把落在内容后的标签栏推到很低的位置。这与截图的现象高度吻合，**但仍需在 8662 浏览器里读取实际 computed style 和样式来源，才能将“主题样式缺失/覆盖”定为最终根因**；不要只根据截图宣布已经证实。

更具体地说，乾坤入口 `cku-mes-bpm/src/main.ts` 引用 `@/plugins/elementPlus`，后者在 `src/plugins/elementPlus/index.ts` 导入 `element-plus/theme-chalk/src/index.scss`（全量 Element Plus 组件样式）。联邦直渲染**不会执行远程 `main.ts`**；它的 `src/fulgurjs/setup.ts` 只导入 `@/styles/index.scss`，该文件没有导入上述 Element Plus 全量样式。这是当前能从源码直接指出的入口差异，也是优先验证的原因链。页面自身的 SVN 差异主要是表单从 iframe 改为联邦组件，`<el-tabs>` 的位置与底部样式没有被直接改动；不要误判为页面模板把标签主动放到了下方。宿主 admin 自有的 Element Plus 版本和 CSS 只能视为偶然环境，不能替 BPM 远程页面承担完整主题样式契约。

**执行者必须完成的诊断。** 在 8662 对同一个实例（可用用户截图中的编号 `5da9127e-b84d-11f1-a9ac-96d848c31a95`，若已不可访问则用同类型新实例）打开详情，用开发者工具记录 `.el-tabs`、`.el-tabs__content`、`.el-tabs__header` 的 DOM 顺序、class、computed `display/flex-direction/height/order/margin`，并在 Styles 面板记录 `.el-tabs--top` 命中的 CSS 文件与层叠结果。检查远程 manifest 的 CSS 列表、实际网络请求、联邦 `loadRemote` 注入的样式、宿主样式及加载时序；与乾坤版同页面、同数据、同视口对比。先确定是规则缺失、覆盖、资源加载失败，还是其他容器尺寸叠加问题。诊断证据需写入最终报告，明确“看到的现象 → 计算样式/网络证据 → 修改的入口 → 修复后计算样式/截图”。

**修复方向。** 优先在 BPM 远程的联邦样式入口补齐该应用在乾坤入口原本依赖的 Element Plus 主题 CSS，使需要的 Tabs、Scrollbar、Card、Form、Timeline 等组件样式在 dev 和 prod 的联邦页面均可靠加载；若不能全量引入，应按组件明确列出样式依赖并验证不会漏项。应处理重复注入与 CSS 顺序，避免两份 Element Plus 版本在宿主全局相互覆盖；如果正式定位为插件未把 setup 或 expose 的 CSS 收进 manifest/运行时，也要修复插件的 CSS 依赖收集与加载，并加有意义的回归验证。不要只在详情页强行写 `.el-tabs { flex-direction: column-reverse !important }` 或手动改 DOM 顺序来掩盖远程样式漏载；也不要为了视觉过关盲调 `height: 95vh`、添加大 z-index 或覆盖所有宿主 tabs。确需调整详情页高度/滚动时，先证明具体父容器和计算值，并限定到该页面，保留预览模式与按钮区行为。

## 6. 最终完成判定

以下全部成立才算完成：

1. 一个只有自己的 `package.json`、`vite.config.ts`、`fulgurjs.config.ts` 的远程工程可独立构建与发布；宿主处于另一个仓库时仅靠公开地址消费它，不需共同父目录或对方源码。Vite 实际代码只需 `import fulgurjsConfig from './fulgurjs.config'` 和 `federation(fulgurjsConfig)`，无加载器、转换器、`await` 和应用名字符串。
