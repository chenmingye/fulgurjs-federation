## 0. 先理解本轮要完成什么

5.1.4 已正式发布，已有验收范围通过；没有证据表明插件尚不能正常使用。本轮要把尚未闭环的故障恢复体验、React 跨应用热更新、Vite 5 特例、示例与验收工具问题做完，并处理 D6 的有效未提交内容、D7 的 Vue/React 完整可复制 demo。

本轮不是实现“任意浏览器、任意模块图、任意业务错误都能同页无损恢复”。浏览器模块加载和框架热更新有边界。用户要的是：能重试的真正重试；需要整页刷新的有明确操作且实际恢复；正常开发不需要用户反复手动刷新；文档不夸大；支持矩阵没有跳过项冒充通过。

**用户追加的硬性要求：每次此类夜间大任务，MES 都必须重新从 SVN 全新检出，再从当前 API 接入开始做；旧测试副本已被用户删除。还必须盘点主仓库未提交的有效示例、代码和文档，把应入库的内容验证后提交并推送，不能因为在新 clone 中工作就遗漏它们。Vue 与 React 示例要明确分组，提供可以直接复制安装运行的完整宿主/远程 demo，不能让使用者从零补工程配置。**

## 1. 必须做的剩余项：事实、目标和通过标准

### D1：Vue 默认错误占位没有可操作的恢复入口

**事实**：`packages/plugin/src/vue-adapter.ts` 的 `RemoteErrorPlaceholder` 只有中文文字。`createRemoteComponent` 和 `createHostPages().component()` 通过 `defineAsyncComponent` 使用它。React 的 `packages/plugin/src/react-adapter.ts` 默认占位已经有重试按钮。

**目标**：Vue 和 React 都提供完整的默认恢复体验，用户不必自己写一整套错误组件才能继续使用。

必须做到：

1. Vue 默认占位增加真正有效的“重试加载”，点击后调用实际远程加载链，不只是清空提示或重新显示旧的失败 Promise。
2. Vue `remoteComponent` 和 `createHostPages().component()` 两条公开使用路径都验收；React 对应路径同步回归。
3. 成功时占位消失、业务组件可操作；多次点击不能创建重复并发加载、双份框架实例或重复会话初始化。
4. 当前公开 API 尽量保持简单，恢复逻辑由插件完成。需要新增或改变公开签名时，先列出实际调用方和最小 API 草案，记录在本轮 `work/design.md`，再实现并同步所有类型和文档。不要为了这个功能新增一堆历史兼容别名。
5. 保留自定义 `errorComponent` / React `error` 能力，说明默认能力和自定义组件的恢复契约；不能破坏已有使用者的自定义占位。
6. 特别回归 Vue KeepAlive：联邦页 → 原生页 → 联邦页、登出、换账号，零 `deactivate is not a function`。上轮代码说明外层无状态包装曾触发这类竞态，不能盲目套一层组件。
7. load 与远程 render 错误分开判断：业务渲染异常不能一律归为网络故障，更不能自动刷新掩盖业务 bug。

**门禁**：两个框架、组件和页面适配器路径都真实阻断远程 entry/expose，再解除阻断后点击恢复，实际业务交互通过；记录请求、错误、恢复 UI 与截图。

### D2：生产静态子依赖失败没有完成用户层面的恢复闭环

**事实**：`e2e/tests/react-prod.spec.ts` 的 B3c 当前允许两个结果都通过：同页恢复，或者错误占位继续存在。它验证了边界，并没有证明恢复完成。只改变 expose URL 不一定能重新执行整个静态依赖图。

**本轮目标和明确方案**：

- entry/expose 自身可恢复的情况继续优先同页“重试加载”。
- 如果失败属于浏览器模块图缓存/求值边界，或者同页重试后仍失败，应向用户提供清楚的“刷新页面重试”操作，并说明整页刷新会清除未保存的本地页面状态。
- 必须由用户明确点击该操作才整页刷新。不要在普通加载失败、每次页面切换、渲染错误、401 或每次重试时自动 reload。
- 完成标准是用户能通过占位内的操作实际恢复目标业务页面；本轮不强求静态子依赖都能同页无损恢复。

实施要求：

1. 可以默认同时提供“重试加载”和“刷新页面重试”，或在一次实际重试仍失败后展示后者。选择一种简单、可解释的规则，Vue/React一致，写入 `work/design.md`。
2. 错误分类必须有依据；浏览器通常不会把具体失败的子依赖 URL 完整交给外层 catch。不能只凭一个通用 TypeError 就声称已经精确识别了静态依赖错误。无法精确判断时，采用透明的通用加载失败恢复选项并如实解释。
3. “刷新页面重试”保留当前 pathname、query 和 hash，不伪造登录 token、不偷偷追加长期随机 URL；遵守宿主自己的认证策略，若宿主要求重新登录就真实登录后继续验证同一目标深链。
4. 防止自动刷新循环，服务仍故障时继续清楚展示错误，不能无限 reload。
5. 保留原始异常 cause、错误码、远程名、spec 与实际请求信息。错误文案以清晰中文表达“现象、原因/可确认的信息、修法”，不把猜测说成定论。
6. 禁止全图随机 query、重写已成功的 shared/React/Vue/Context 模块、blob/eval 下载源码、iframe 新运行环境、手改 node_modules 等投机做法。不能以恢复为代价破坏模块身份、CSP、CSS、base、单例或懒加载。
7. 如果你找到范围明确且经验证的同页恢复办法，可以采用，但必须先证明成功共享模块身份、两个 expose 同 chunk 身份、并发失败单代次以及冷启动懒加载不退化；不要把“换入口 URL”当成对子依赖生效的证据。

**必须改写的测试**：把 B3c 从“两个结果都能 PASS”改成确定门禁。真实阻断静态 leaf → 首次明确错误 → 解除故障 → 同页恢复成功，或插件占位的刷新操作真正导航后成功 → 正确 leaf 值与业务按钮通过。失败占位一直存在不能 PASS。

必须增加 Vue 对应静态依赖用例。测试监听和故障路由在任何登录/导航/挂载前安装；截图至少包含错误态、可操作的恢复按钮、恢复后的实际页面。断网、HTTP 404/503、模块求值抛错分别记录，不把它们笼统说成“浏览器全部缓存失败”；求值异常若源码未修复，刷新本来也不能修复，必须如实保持失败。

### D3：React 跨 origin 开发热更新仍依赖测试脚本手动刷新

**事实**：`e2e/tests/react-dev.spec.ts` 的 R11 先等 3 秒；未自动更新时调用 `page.reload()`，再把新代码可见作为通过。README 的总览同时写“全链路 HMR/状态保留”，与详细章节的跨源限制存在表达冲突。

**目标**：正常支持范围内的开发更新由插件与 Vite 自动传播；用户不用每次修改远程源码后自己刷新宿主。

按以下三类明确处理，不能混为一谈：

| 类型 | 本轮完成契约 |
| --- | --- |
| 框架支持的组件更新，例如 React 单组件模块改显示文本、Vue 改 template | 不由测试脚本刷新；实际热更新出现；React Hooks/Vue 本地计数在兼容改动下保留 |
| 普通 TS 数据/函数依赖变化 | 已挂载宿主实际看到新值，不只测试新的独立 import；传播方式和是否重新挂载如实记录；不能以用户手动刷新算完成 |
| React Refresh 不兼容的导出/Hooks 结构变化、Vite 要求 full-reload 的改动 | 可以按框架标准触发自动重新挂载或明确的 full-reload；不能承诺任意改动保留状态；必须有稳定的错误与恢复路径 |

实施排查顺序：

1. 在真正冷启动下捕获宿主/远程 client 连接、WebSocket 握手、首次 update 帧、实际模块 URL 和接受边界；区分 WS 未连接、更新没有传播、已传播但 adapter 缓存仍旧、React Refresh runtime/preamble 不一致。
2. 检查 `packages/plugin/src/index.ts`、`virtual.ts` 生成的远程 dev client、模块路径、React shared 门面及 adapter 缓存。源码没有独立 `src/dev.ts` 文件，不要按旧任务书虚构这个文件。
3. 同时覆盖宿主先起、远程先起、从已有登录导航进入、直接打开深链、remote 暂停后重连；监听注册要先于更新。
4. 使用 Vite 已有 plugin/HMR hook、模块图与允许的事件通信；如果需要联邦专用更新消息，只在 dev 启用，对实际注册远程校验来源/spec，去重并处理 dispose，不在 prod 加 WebSocket 或定时轮询。
5. 不复制一份 React，不对成功的 Context/shared 模块加随机参数，不靠 setInterval 循环 import，也不把所有更新都变成整页刷新来假装 HMR。
6. 同一普通 React 文本改动至少连续执行 5 次冷启动，每次 3 次修改/恢复；必须零人工 `page.reload()`、零偶发 fallback 放行。Vue 对应既有状态保留用例同时回归。
7. 记录每次更新前后的文档导航计数、组件计数、DOM 文本和 WS 事件。如果 full-reload 是产品按不兼容边界触发，单独归类；不能把 reload 后成功计入“组件热更新保活通过”。

**测试变化**：拆分/改写 R11 为严格自动传播门禁；删掉“没热更就由测试脚本刷新也算过”的分支。普通兼容组件更新要验证不发生整页导航，实际 local state 保留。

推送前重新 fetch 核对远端是否有人更新；有变化就正常整合并重做受影响门禁，不 force push 覆盖他人提交。现场验证 latest、tag、Release、发布 run、registry tarball SHA512 与 integrity 一致、provenance subject/source commit 和实际包内容。不停在“Git 推上去了”。
