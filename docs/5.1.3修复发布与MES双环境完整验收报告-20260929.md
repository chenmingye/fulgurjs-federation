## 1. 剩余问题根因与修复

### 1.1 问题 A：TS 应用配置上下文识别（`packages/plugin/src/dts.ts`）

- **根因**：`hostPathsCovers()` 扫描根目录全部 `tsconfig*.json`（仅排除 `tsconfig.node.json`），任何一份无关配置（如 `tsconfig.test.json`）出现 `<remote>/*` paths 即误判「应用已接管」，抑制应用导入所需的 ambient 声明（真实复现：无关 `tsconfig.test.json` 携带真实 paths → 返回 true）。
- **修复**：按真实 TS 上下文判定——
  - 主配置选择：`tsconfig.json` 优先；无主配置时取唯一候选或「唯一 include 覆盖应用源码/类型输出目录」的候选（覆盖只有 `tsconfig.typecheck.json` 的工程）；多候选无法唯一确定 → 安全回退（生成默认宽松声明，导入可解析）+ 中文诊断。
  - `references` 语义过滤：solution 型（`files: []`）配置自身不判定；被引用的子项目按「include 覆盖应用源码或类型输出目录」判定，不再按文件名排除。
  - `extends` 链继承 paths；paths 目标与 baseUrl 按声明所在配置的目录解析（继承自父目录配置的 paths 不再按使用方目录误算）。
  - 精确键与通配键语义保留：仅通配键 `<remote>/*` 算接管。
- **回归**：`tests/dts-paths-covers.test.ts` 16 用例（8 场景单测 + 真实 tsc 端到端：无关测试配置不抑制 ambient、应用接管后精确轨拒绝错误 props/合法 props 通过）；全量单测 478/478；typecheck pinned+latest 通过。
- **文档**：中英 README「任一 tsconfig」表述订正为「应用 TS 上下文」语义。

### 1.2 问题 B：生产重试与模块身份（`packages/plugin/src/virtual.ts` genProdRetryHelper）

- **根因**：per-URL 状态机在并发失败时每个失败各自递增代次并改写当前 URL——并发中的其他调用可能落到不同 `fulgurjs_retry` 代次 URL（不同 module map 条目 → 模块重复求值、单例身份分裂）。
- **修复**：per-URL **promise** 状态机——并发调用共享同一 Promise（单请求、单失败、每代次只推进一次）；成功缓存定型 Promise（重复访问零额外网络请求、身份严格保持、两个 expose 别名同 chunk 同样去重）。
- **真实构建浏览器验证**（隔离 nginx prod，fixturesremote-react 构建 + host-react 消费）：
  - B1 别名身份：两个 expose 别名指向同一源码 → manifest 合并为同一 chunk → 并发加载 identity:same、模块求值 1 次、重复访问零新增请求、成功 URL 零 retry 参数（e2e prod-react B1）。
  - B2 并发失败：阻断 chunk → Provider+面板共享同一失败 → 解除后恢复请求 URL 恰为 `fulgurjs_retry=1`（单代次推进的直接证据）→ 恢复后身份/求值正确（e2e prod-react B2）。
  - B3a 入口失败 → 解除 → 同页重试恢复 ✓（e2e prod-react B3a）。
  - B3b expose chunk 失败 → 解除 → 同页重试恢复 ✓（e2e prod-react B3b）。
  - B3c **静态依赖失败边界（如实记录，非 PASS 项）**：expose 的静态子依赖 chunk 失败后，同页重试不可恢复——浏览器 module map 缓存了该依赖 URL 的失败，重试换 URL 的 expose chunk 重新拉取后其静态 import 仍命中缓存失败（真实浏览器证据：facade retry=1→retry=2 单调推进，leaf 零网络事件；`evidence/5.1.3-b-retry/`）。恢复需整页刷新。插件不做全站依赖图递归改写（任务书边界）；已写入中英 README 边界说明。
- **回归**：`tests/prod-retry-helper.test.ts` 10 用例（黑盒 data:URL 真实 import + 白盒 URL 序列 + 并发单代次推进回归）；e2e prod-react 11/11。
