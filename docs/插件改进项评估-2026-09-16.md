## D.1 远程 SFC 静态导入 `virtual:fulgur-runtime` 的 dev 检测 —— ✅ 已实现

**问题**：远程应用的页面 SFC 若静态 `import 'virtual:fulgur-runtime'`，dev 下渲染上下文被破坏
（resolveComponent / withDirectives / "Missing ref owner" 三件套告警，内容区静默空白），
插件侧无任何报错。本轮实测排障耗时约 40 分钟（二分定位）。

**根因**：虚拟模块由远程 dev server 求值，会在远程模块图内实例化一份独立 runtime，
SFC 的渲染 setup 绑定到错误的应用上下文。正确姿势是 `globalThis.__FULGUR_RUNTIME__`
（宿主已初始化的单例，见 manual/迁移指南与 bpm `detail/index.vue` 内注释）。

**✅ 实现（dev-only）**：post.transform 阶段检测——当被转换文件是 **exposes 目标文件**
（`isExposeTargetFile`，支持无扩展名声明与 .vue script 子请求匹配）且源码含该虚拟模块
导入时，`this.error` 显式拦截，报错文案三段式（现象/根因/修法）并指向迁移指南三B-1 节。
只拦 exposes 目标：宿主侧页面（如 admin FulgurDemo）静态导入是合法用法，不受影响；
build 不拦（prod 各副本经 globalThis 单例收敛）。单测 5 例（命中/扩展名推导/宿主侧
不命中/跨项目不命中/文案三段式）。

**排期**：已落地（随下一版本发布）。

## D.2 带参路由 expose 键冲突告警

**问题**：宿主侧路由表（如 admin `fulgurPages.ts`）从带参路由推导 spec 时剥离 `:param`
（例：`model/:type/:id` → `pages/bpm/manager/model`），与列表页 expose 键收敛相同时静默错配
——曾实际导致"复制流程"误走"更新"语义（数据风险，见遗留任务交接清单 §2.1 纠偏）。
目前只能靠人工写 `spec` 显式覆盖规避。

**方案**：路由表在插件视野之外（应用侧数据），插件无法直接感知。两条路：
1. 提供 `defineFulgurPages()` 帮助函数（官方 API），构建/启动期做重复 spec、参数剥离收敛检测并告警；
2. 轻量版：文档化"带参路由必须显式 spec"的检查清单 + 在 dev 容器入口对宿主注册的路由参数做运行时探测告警（可行性一般，易误报）。

**可行性**：中——需要新增 API 面（方案 1）或接受文档约束（方案 2）。方案 1 与宿主侧 API
官方化方向一致，但涉及设计决策（路由表 schema 是否收进插件）。

**排期建议**：中期，v0.3.x~v0.4，与宿主侧路由映射 API 官方化一批做；**实现前先出设计方案供用户审阅**。

## D.4 expose 子树依赖副本收敛（2026-09-16 深夜诊断，testbed 实测）

**现象**：lowcode prod 产物 70MB / 1099 个文件，出现多份近同的依赖子树 chunk——3 个
5.6MB index chunk（内联 monaco 族）、5 份 domUtils 级 2.4MB chunk 两两 99.97% 相同
（仅依赖 hash 引用不同）、en locale `total:"Total {total}"` 出现 10 处、
`Symbol("localeContextKey")` 多份。单个页面首屏解码量 13.8MB。

**根因方向**：联邦构建按 expose 划分子树时，同一依赖（element-plus/avue 栈）在每个
expose 子树内各实例化一份副本，rollup 未能按 resolved id 收敛（具体机制待查：
疑与 expose facade 的按消费方绑定/虚拟模块 id 有关，使同一文件以不同模块 id 进入图）。

**影响**：① 包体与首屏解码量按副本数膨胀（性能）；② **provide/inject 按 Symbol 键
副本隔离**——跨副本的 app 级 provide 无法命中（已实测：宿主侧与远程侧三处 provide
均验证落上宿主 app context 且值正确，但 avue-crud 内 el-pagination 仍渲染英文
Total），element-plus 这类带 provide/inject 全局配置的库在多副本下国际化/全局配置
失效。乾坤单应用形态只有一份 EP 副本所以无此问题。

**方案候选（需设计评审）**：
1. build 期识别「跨 expose 重复实例化的重依赖」并收敛为共享 chunk（插件级 chunk 去重）；
2. 文档化指导：把 element-plus 这类「带全局配置面的大依赖」声明进 shared，走协商门面
   收敛为单副本（需验证 UMD 依赖 avue 的 require 链在此形态下的表现）；
3. 短期缓解：低代码页面自身经 ElConfigProvider 包裹（同子图键必然同副本——待验证
   avue 内部渲染的分页是否与页面同副本，本次实测薄壳包裹未生效，说明副本切分发生在
   页面子树内部，此路存疑）。

**验证口径**：修复后 lowcode dist 体积、单页解码量、以及「共 N 条」中文分页应同时达成。
