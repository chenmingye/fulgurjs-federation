### 2.2 `check-pages` 仍会找错 manifest，旧聚合配置还能把本地旧产物当线上通过

证据：`packages/plugin/src/commands.ts` 的 `fetchRemoteManifestApp()`（目前约第 337–367 行）把绝对 `prod/external` 字符串直接当目录拼 `/fulgurjs-manifest.json`，没有处理插件公开支持的完整 `fulgurjs-remoteEntry.js` URL 与 `name@url` 形态。在隔离配置中，同一远程写 `http://localhost:8662/flowable` 时 `--require-verified` 通过；改成 `http://localhost:8662/flowable/fulgurjs-remoteEntry.js` 或 `mes-bpm@http://localhost:8662/flowable`，运行时支持的配置形态仍合法，但 `check-pages` 报“无法验证”。

`fetchRemoteManifestRepo()`（目前约第 307–334 行）把本地 `dist` 排在显式 `--site` 前。本次用一个本地有效 manifest 加 `--site http://127.0.0.1:1 --require-verified` 实测 **退出码仍为 0**，`manifestSources` 明示用了本地 `dist`。这违背 README 和上轮任务书“`--manifest` > `--site` > 本地 dist”的承诺；指定站点不可达时应标“无法验证”，严格模式退出非零。

修法与验收：统一采用插件运行时对 remote 地址的解析语义来推导 manifest，兼容目录 URL、完整 entry URL、`name@url`、对象 `{ dev, prod, external }`、相对和绝对 prod 地址，避免 CLI 自己再维护一套不一致的字符串拼接。`--manifest` 或 `--site` 被明确指定时，只用指定来源；来源失败直接报告，不得回退到旧本地 dist。无显式线上来源时，旧聚合配置才可按已文档化顺序回退本地产物。每种地址形态加正反用例并断言退出码和 `manifestSources`；用 registry 正式包再次复现，不能只测源码函数。

### 2.3 独立目录里的 TypeScript 配置可能被旧 esbuild 拒绝

证据：`packages/plugin/src/app-config.ts` 的 `resolveEsbuild()`（目前约第 187–209 行）按配置目录、CLI 自身位置找**第一个能解析到的 esbuild**，不检查它能否解析模板要求的 TS `satisfies` 语法。当前安装的 CLI 自身路径能解析到 esbuild 0.11.23，而 Vite 6 项目内的 esbuild 是 0.25.12。把合法的 `export default { name: 'isolated-host', remotes: { ... } } satisfies ...` 放到无本地 Vite 的临时目录，再用已安装的 4.2.1 CLI `explain --config /该目录/fulgurjs.config.ts`，实测 `Expected ";" but found "satisfies"`、退出码 2。三个 MES 项目当前都装有 Vite，因此本次并非证明它们已失败；它说明 CLI 面向独立目录/初始化阶段的能力不够稳定。

修法与验收：选择能解析当前生成模板语法的受控编译器，或在检测到旧编译器时明确切换至兼容版本；不要按“找到就用”选择偶然悬挂的旧版。新增从**与仓库和其他项目不共用配置、没有本地 Vite 的独立目录**运行 `init → explain` 的测试，覆盖 Node 18、当前 LTS、pnpm 严格依赖布局及 TS 相对导入。若产品明确要求先安装 Vite 和插件才能 `explain`，则 CLI 在缺依赖时给出可执行提示，并在 README/起步输出中写清前置条件；不能输出难懂的 esbuild 语法错误。

## 三、懒加载的真实行为与当前性能风险

### 3.1 插件已有按页面加载，不需要再发明一个懒加载 API

宿主 `src/fulgurjs/host/pages.data.ts` 的 26 条记录只是路由到远程 expose 键的**数据映射**，声明十几页并不等于把十几页组件 JavaScript 都导入宿主首屏。`src/fulgurjs/host/pages.ts` 调 `createHostPages()` 后，`packages/plugin/src/vue-adapter.ts` 对页面建立 `defineAsyncComponent` 包装；只有该组件真正渲染时，`loader` 才运行 `beforeLoad → loadRemote(spec)`。`loadRemote` 获取所需远程容器和共享依赖、为当前模块预载清单中的 CSS、执行该远程的应用级 `setup`（首次）和当前会话的 `onSession`，再调用 `container.get(module)` 加载**选中的 expose**。已加载模块有 Promise 缓存；再次打开同一页面通常复用模块，换账号会重做会话初始化而不重新下载 JS。`remoteComponent('remote/X')` 也是 `defineAsyncComponent` 包装，普通 TS 函数 expose 只有业务代码调用 `loadRemote('remote/X')` 时才加载。

因此，**单看联邦组件的加载路径，第一页不会自动执行 BPM 的所有页面模块**。但首次进入任一 BPM 页面仍可能下载远程入口、manifest、共享依赖、BPM 的 `setup`、页面所需共同 chunk/CSS；这些是首次使用远程的必要成本，不能承诺“一次只下载一个文件”。对于同一 chunk 被多个 expose 共享的情况，加载一个页面也可能带入共同代码，这是正常打包结果。

### 3.2 MES 宿主当前的“空闲预载全部远程”会提前下载全部页面资源

`cku-mes-admin/src/fulgurjs/host/bridge.ts` 目前把 `PREFETCH_REMOTES` 设为 `['mes-bpm', 'mes-lowcode']`。宿主进入可解析的联邦页面时调用桥，桥按登录代次安排 `requestIdleCallback`（无 API 时 1.5 秒后）执行 `preloadRemote(name, { mode: 'prefetch' })`。这里传的是**远程名而非某个页面名**。`packages/plugin/src/runtime/index.ts` 的 `preloadRemote` 在无 `module` 参数时选择 manifest 的 `entries` 全部条目，为每个 expose 插入 `modulepreload` 链接和 CSS `stylesheet` 链接；`fetchPriority='low'` 只是降低优先级，不保证浏览器不下载。它预取模块资源，但并不调用 `container.get()`、不执行全部页面组件。`setup/onSession` 仍由真实页面 `loadRemote` 触发。

本次在 **8662、全新浏览器缓存、1600×950、管理员登录** 下做了只读网络复核：登录后停留 dashboard，BPM 与 lowcode 的 expose 文件请求都是 **0**；首次打开 BPM 待办页约 0.7 秒后仍没有 expose 预载链接；约 6.2 秒后，BPM manifest 对应的 **21 个不同 expose 文件全部出现预载链接并完成网络请求**，lowcode 的 **8 个不同 expose 文件也全部出现链接并完成请求**。manifest 中 expose 键数是 BPM 24、lowcode 8；BPM 多个键共用同一个构建文件，所以按“不同文件”计数为 21。测量对照的是同一构建 manifest 的文件 URL 与浏览器 `link[rel=modulepreload]`、`requestfinished`，未把共享 chunk 误算为独立页面。这说明当前是“**组件按需执行，但第一次进入任一联邦页后，两个远程的全部公开页面文件会被提前下载**”。具体耗时和字节数受缓存、网络与打包影响，本次没有给出统一字节预算；不能断言每台机器必然变慢，但存在明确的首访带宽与 CSS 注入成本。

### 3.3 本轮建议的性能目标与实施要求

保留插件现有按页加载机制；本轮主要改 MES 宿主的预载策略，让默认首次访问保持真正的网络按需加载：

1. 不再在首次联邦页面访问时无条件 `preloadRemote('mes-bpm')` 和 `preloadRemote('mes-lowcode')`。推荐默认关闭这两个“全远程”预载，或仅针对用户下一步很可能打开的**一两个明确 spec** 做低优先级预取，例如 `preloadRemote('mes-bpm/pages/bpm/task/todo', { mode: 'prefetch' })`。是否预取具体页面由实际用户路径和网络数据决定；不要为了跑验收而把大量页面藏进另一个定时器继续预载。插件的显式 `preloadRemote(name)` 能力继续保留给确实要预热整个远程的项目。
2. 在 README 加一节清楚解释四层：**路由表声明**、**真实页面模块加载**、**`preloadRemote('remote/page')` 单页预取**、**`preloadRemote('remote')` 整个远程预取**；说明 `setup` 的一次性成本、会话重复初始化、共享 chunk，以及“预取是下载，不等于执行”。不要把当前全远程预取宣传成完全懒加载。
3. 在 dev 与发布后 8662 生产形态，用新浏览器上下文与禁缓存/冷缓存分别记录：登录停在 dashboard、首次打开 BPM 待办、再打开另一个 BPM 页面、首次打开 lowcode、重复打开已访问页面。按 manifest 的 **不同 expose 文件 URL** 统计网络请求和 `modulepreload`，另列 remoteEntry、setup、共享 chunk、CSS 的请求与传输字节，记录各阶段耗时、首个可交互时点、错误和截图。验收目标：dashboard 不加载两个远程页面文件；首次 BPM 页不批量下载 BPM 所有页面文件，也不下载 lowcode 全部页面文件；第一次进入 lowcode 才加载其所需模块；重复进入同页不重复下载；主动指定整远程预载时才允许全清单下载。dev/prod 都测，不能只用 manifest 文件数推断浏览器实际流量。
4. 若发现某个业务页因 chunk 粒度过大而把大部分页面代码打入共同 chunk，要测**实际字节数**并针对构建拆分问题优化；不能只改预载白名单就宣布性能解决。CSS 加载和双版本 Element Plus 的样式顺序要回归审批详情标签栏及其他 BPM 页面，避免性能调整让原视觉 bug 回来。
