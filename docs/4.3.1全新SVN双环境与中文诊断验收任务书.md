## 1. 本轮究竟要证明什么

4.3.1 相对 4.3.0 的插件改动是：

1. `MFU-010` 仅在**最终选择的共享单例版本不满足消费方 `requiredVersion`** 时出现。多个版本共存、但选中版本满足要求时不能报错。真正不兼容时给出中文的现象、原因、影响、修法；同一版本组合多次加载只警告一次。`strictVersion: true` 对兼容版本应正常加载，对不兼容版本应抛 `MFU-003`。
2. 插件自身的配置、共享依赖、远程加载、类型生成等诊断改用中文。保留错误码、API/配置字段名、版本号和第三方底层异常原文，这些技术标识不要求强行翻译。
3. 移除将普通 npm 包子路径（如 `@vue/runtime-dom`、`vite/modulepreload-polyfill`）猜成“漏配联邦远程”的构建期提示。真正无法解析的模块仍应由 Vite/Rollup 报错，不能把真实错误吞掉。
4. 上轮 MES 宿主的 `single-spa minified message #1` 根因是关闭乾坤后仍静态导入乾坤模块。**那三个宿主源码修正只存在于已删除的 SVN 测试副本，没有随插件 Git 包发布。** 本轮全新接入时必须重新实现和验证“乾坤关闭时不加载其运行时”的门控。它是项目侧接入问题，不应误归为插件诊断。

验收必须同时覆盖：正式 npm 包来源、全新 SVN 接入、dev、8662 生产形态、真实业务功能、懒加载、账号/会话、故障恢复，以及**故意触发错误并保存可读中文提示的截图**。正常路径“没有错误”和负向路径“错误按预期出现”是两项不同的断言。不要用单测、构建通过、页面有字、旧截图或旧 JSON 替代本轮浏览器证据。

### 4.1 共享版本协商：兼容时安静，真正冲突时中文告警

用**已安装的 registry 4.3.1** 创建一个极小 Vite 浏览器 fixture，或在现有隔离 fixture 中建立专用页面，静态导入 `@fulgurjs/federation/runtime` 的 `initSharing`、`registerShare`、`loadShare`。使用独立 shareScope 避免全局运行时状态相互污染。

下面是最小触发思路，执行者应把它放进真实 Vite 页面并让浏览器执行，不能只在 Node 中打印预设字符串：

```ts
import { initSharing, registerShare, loadShare } from '@fulgurjs/federation/runtime'

initSharing('diag-compatible-431')
registerShare('diag-compatible-431', 'pinia', '2.1.7', async () => ({ version: '2.1.7' }), { from: 'host' })
registerShare('diag-compatible-431', 'pinia', '2.3.1', async () => ({ version: '2.3.1' }), { from: 'remote' })
await loadShare('pinia', { shareScope: 'diag-compatible-431', requiredVersion: '^2.1.7', singleton: true, strictVersion: true })
// 此时应无 MFU-010/MFU-003。以下使用新 scope，避免上一组已加载实例干扰。
initSharing('diag-incompatible-431')
registerShare('diag-incompatible-431', 'pinia', '2.3.1', async () => ({ version: '2.3.1' }), { from: 'remote' })
await loadShare('pinia', { shareScope: 'diag-incompatible-431', requiredVersion: '^3.0.0', singleton: true })
await loadShare('pinia', { shareScope: 'diag-incompatible-431', requiredVersion: '^3.0.0', singleton: true })
// 以上两次调用合计只应由插件输出一条真实的 MFU-010。
try {
  await loadShare('pinia', { shareScope: 'diag-incompatible-431', requiredVersion: '^3.0.0', singleton: true, strictVersion: true })
} catch (error) {
  console.error(error) // 显示真实抛出的 MFU-003，不自行拼接错误文案
}
```

1. **兼容多版本反证**：在测试 scope 注册 `pinia` 2.1.7 与 2.3.1，分别标注提供方；调用 `loadShare('pinia', { shareScope, requiredVersion: '^2.1.7', singleton: true })`，再以 `strictVersion: true` 调一次。断言实际选中实例可用、两次均无 `MFU-010`、无 `MFU-003`。再为 `vue-router` 用 4.4.5 与 4.6.4、要求 `^4.4.5` 做同类验证。这对应用户原始控制台里的两组误报。
2. **真实冲突正例**：另建一个 scope，只注册 `pinia` 2.3.1，要求 `^3.0.0` 且 `singleton: true`。连续调用两次，断言浏览器 console 恰有**一条**真正由插件产生的 `MFU-010`，内容中文说明“实际版本不满足当前应用要求”，并能看到要求范围、实际版本/提供方、影响和修法。打开浏览器 DevTools 的 Console，截图让完整告警可读；保留 JSON 中的 message、source、时间与调用次数。该 fixture 不必伪造业务页面错误。
3. **严格版本拒绝**：在独立 scope 或清空 fixture 运行时后，用相同不兼容版本启用 `strictVersion: true`，`catch` 并展示真正抛出的 `MFU-003`。断言错误码与中文诊断都来自插件。截图包含页面的失败/处理状态和 Console 中的原始错误；完成后恢复到兼容配置，再截图无告警的状态。

以上三步的断言要区分 `console.warn`、`console.error`、`pageerror`；不能因为把告警过滤掉而声称“没有发生”。测试结束删除或隔离故障 fixture，不让它参与 8662 正常站点构建。

## 7. 判定规则、失败处理与最终交付

最终报告首页列：Git tag/commit、GitHub Release 与 publish run 状态、npm registry `latest`、完整 tarball URL/integrity/provenance、三应用 package/锁文件/node_modules 的 4.3.1 证据、SVN URL/revision/初始与最终 status、dev 与 8662 的访问地址和服务状态。附逐项表格：实际执行、预期、结果、原始 JSON/日志、截图相对路径、失败或外部噪音的归因。**截图索引必须能让用户打开后直接看清真实中文错误文本、发生环境和恢复状态**；终端错误用终端截图，浏览器错误用实际页面与 DevTools Console 的截图，不能用 Photoshop、手写 HTML 或截图覆盖文字制造“复现”。

通过标准：正式包来源全一致；配置与静态门禁通过；兼容版本零误报、不兼容版本一次中文 `MFU-010`、严格冲突 `MFU-003`、远程故障 `MFU-001` 和配置错误都真实触发且可读；正常 dev 与 8662 没有插件引起的异常；全部实际菜单/页面与业务闭环通过；两环境懒加载和故障恢复通过；8662 留站；SVN 从未提交。权限码时序、第三方库、原项目接口等噪音只在有明确来源和复测证据时单列，不算插件缺陷；错误页绝不计入页面通过数。

发现插件本身新缺陷时先定位并补有意义的回归测试，按用户长期偏好更新版本、Git 提交推送、创建 Release 并确认 npm 正式包，三应用重新从 registry 安装**最终版本**，受影响场景与 dev/8662 全量验收重跑，旧版截图不能充数。发现的是 MES 接入缺陷时只改本地 SVN 测试副本并重验，仍**绝不提交 SVN**。若客观条件阻塞，报告已完成与未完成项及证据，不写“完美验收”。

交付 `docs/MES-ZC-SVN验收报告-4.3.1.md`（若最终发布了更高补丁版，文件名用最终版）与本轮证据索引；更新受影响 README/迁移文档和测试脚本；应进入插件 Git 的文档与脚本提交并推送远端。测试结束只清理由本轮启动且确认归属的临时 dev/fixture 进程与无敏感性的临时文件，**不停止 8662**。最后再做一次 `svn status`、8662 HTTP/监听和 Git 状态核对。
